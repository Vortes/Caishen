# Book imports from precedent instead of asking for approval

ADR 0003 and ADR 0004 describe an agent that proposes categories and matches for the user to approve in bulk from a daily review. That is YNAB's approval queue with a better suggestion engine, and the queue is the tedium Caishen exists to remove: when it is not kept up, the budget stops matching reality and people start over. We decide instead that the agent does the bookkeeping. It books every bank import, and the user's side of every partner's purchase, on arrival, marks what it did, and asks only when being wrong would misstate money between people or between the user and the bank. The user feels the agent by what gets done, not by what waits for them.

- **Authority.** The agent changes what happened, never what the user planned. It may set categories, shares, transfers, and matches. It never assigns, moves money between envelopes or to or from Ready to Assign, proposes a funding plan, or covers overspending. The accounting engine refuses an agent-sourced operation that would assign. Ready to Assign and category balances still move as the consequence of booked facts such as income, refunds, and reclassified transfers.
- **Doing, not proposing.** A booking is applied as a reviewed transaction. Nothing waits on the user, and one tap corrects a booking. The agent only sets what is empty or what it set itself; it never changes a category, share, or match a person chose, even when it is sure the person was wrong. Manual entries the user typed are never booked. When the agent first runs on a budget, it books the whole backlog of unreviewed imports and leaves reviewed transactions untouched.
- **Precedent is the unit of learning, not the payee.** A precedent is a choice the user made together with the facts of that import: payee, location and store number, amount, account, day, and time. The agent books with precedent when a new import matches one on the facts that distinguish it from the others, and the booking names that fact. Two precedents at one payee that disagree, such as one Costco where the user's mother shops and another where the user does, force the agent to find the separating fact or guess. A guess is still booked, marked as guessed, and listed near the top of the daily review. A guess becomes precedent when the user corrects it or leaves it alone after seeing it in a daily review they opened; time alone never upgrades it. Correcting a booking offers, inline and never automatically, to change the other bookings made from the same precedent. Payee memory stays as the prefill for manual entries; it is not precedent, because it remembers only the most recent choice per payee.
- **Shares.** A share is applied only from precedent. A new payee is booked as entirely the user's own. No share question reaches the review inbox.
- **Evidence.** The agent reasons over the import record and the user's own budget and history. It may look up public facts about a merchant, such as the location a store number names, sending nothing about the user. It never reaches the user's calendar, email, or device location, or the partner's private categories. The import record keeps Plaid's location and store number fields for this purpose, under the data retention policy.
- **Questions.** The review inbox holds only uncertain matches, unexplained discrepancies, transfers with no found other side, and anything else where a wrong answer would misstate money between people or against the bank. Each item is a question with a proposed answer and one-tap acceptance. A category guess is never an inbox item. Reconciliation stays as ADR 0003 states it: the agent explains discrepancies and never adjusts to force a match.
- **Presence.** No chat surface and no persona in the first version. The agent is visible through a mark on each row it touched, a register filter for its work, and the daily review, which reads in this order: questions, guesses, handoffs, then bookings with precedent as a count with a way in. Any future character shows only real agent status and never asks for anything bookkeeping does not need.
- **Payee.** The bank's merchant name when it provides one, otherwise the raw statement descriptor, never rewritten by Caishen, with the raw descriptor kept on the transaction so it ties back to the statement.

## Considered options

Keeping the approval queue with better suggestions was rejected because the queue is still the user's, and a queue not kept up is the failure mode this app exists to prevent. A global training period in which the agent watches and books nothing until its suggestions match the user was rejected because it makes the agent useless on a new budget for weeks, which is when the backlog hurts most; the per-payee handoff gives the same "watched you, now doing it" moment and is true per precedent rather than staged on one day. Learning per payee was rejected because one payee can carry several of the user's intentions, which only the import's other facts separate. Inventing a share for a plausible-looking new payee was rejected because every new restaurant would become a question and flood the inbox. Upgrading an uncorrected guess after a fixed time was rejected because it decides the user agreed when they were merely busy. Rewriting payees to clean merchant names was rejected because the raw descriptor is what ties a row back to the card statement. A chat surface was rejected because it invites delegating budgeting, which the authority rule forbids.

## Consequences

The glossary's Daily review and Review inbox entries change from an approval model to this one, and the agent-engine decision's "proposes categories" now means booking under this authority rule. Booked transactions count as reviewed, so the inbox count no longer includes them. The voice of the daily review and the row mark, a quiet status versus a character, is deliberately undecided and will be chosen from two prototypes. Model provider and inference path remain separate from accounting operations as ADR 0003 requires; the first provider choice is made at implementation time.
