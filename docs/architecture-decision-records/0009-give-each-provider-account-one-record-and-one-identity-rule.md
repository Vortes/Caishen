# Give each provider account one record, one lifecycle, and one identity rule

A provider account was a cache entry keyed by Plaid's `account_id`, kept in four parallel lists on the bank connection row: the account catalog, the ready list, the unavailable list, and the mapping to budget accounts. Plaid documents that `account_id` can change, and when it did the lists disagreed and only code could notice. Reconnecting created duplicate connections and duplicate budget accounts, choosing a subset of cards during authorization hid the others, and Add accounts created the duplicates again; each fix was correct and each next incident found another path to the same result, because the budget account row knew nothing about its feed and the database could not refuse a second feed or a mapping with no identity behind it. We give each provider account one row with its own identity and lifecycle, record each live feed as its own row with constraints the database enforces, and answer "is this the same account?" through one ranked ladder shared by every path.

- **Records.** A `BankAccount` row is one provider account inside one bank connection: Plaid's account id, the persistent account id when Plaid provides one, name, official name, mask, type, subtype, currency, balances with their as-of time, status, readiness, first and last seen times, and a reference to the row that superseded it. It is unique on connection and Plaid account id, and unique on connection and persistent account id among shared rows. A `BankAccountLink` row is one feed from a provider account into a budget account, with its start date, opening snapshot, and linked and unlinked times. A link is unique on its provider account, and a budget account has at most one live link; a link without a provider account row cannot exist. The database, not code, therefore refuses two live feeds into one budget account and any feed with no identity behind it.
- **Lifecycle.** A provider account has four states and five transitions. This state machine is the decision, not an illustration:

  ```
  shared ──account update omits it──► unavailable
  shared ◄──user re-shares it──────── unavailable
  shared ──USER_ACCOUNT_REVOKED webhook──► revoked
  shared ──same account, new id (superseded)──► retired
  unavailable ──a new provider account takes its place──► retired
  ```

  In every state the linked budget account's history, transactions, and reconciliation never change. An omitted account becomes unavailable and its feed stops; re-sharing restores updates on the same budget account; a revoked or retired account keeps its budget history.
- **Connection status.** A bank connection is connected, login required, pending disconnect, revoked, or disconnected. The status is set from Plaid's Item webhooks and `/item/get` during each account update, never inferred from an account being omitted. The daily account update remains the backstop, so ADR 0004 holds; webhooks make updates sooner and are not required for correctness.
- **Identity ladder.** One module answers "is this the same account?" for Link completion, reconnect, account update, and Add accounts, trying these rungs in order: (1) same connection and same Plaid account id is the same account; (2) same connection and same persistent account id is the same account, and the old row is superseded automatically; (3) same institution with exact name, mask, type, and subtype, where the old Plaid id is absent from the current response, is a recovery candidate the user confirms, and never when more than one candidate matches; (4) anything weaker asks the user and shows masks, and is never automatic. Every automatic resolution is recorded on the operation with the rung that fired. A mapping is in recovery only when its id is absent from the current response, and an ambiguous match is skipped.
- **What does not change.** The accounting engine, change sets, budget `Account` rows, `BankImport` rows, the explicit setup step, and the review inbox are untouched. Import rows keep naming the Plaid account id and reach the budget account through the provider account row and its supersession chain, so an old import row still resolves after an id change without rewriting history. No budget account is created automatically by an account update. Budget history is never deleted for a de-selected account. No match is made on name alone, and import rows keep their list of provider ids rather than a key on a single provider transaction id.
- **Rollout.** Stored shapes change only by addition. The release that reads the new tables ships before the release that writes them, a one-time copy moves the existing JSON lists into rows, and stored samples and contracts cover both forms during the transition. ADR 0008 suspends these ADR 0006 rules until launch; this migration follows them anyway, because the lists it replaces are the data at the center of the incidents. The four parallel lists are retired once the tables are the source, and readiness becomes a field on the provider account row rather than a separate list.

## Considered options

Keeping the four JSON lists and adding an invariant test over them was rejected because a test proves the code of one release against data it generates, while the lists disagree in production under code that already passed; the database still could not refuse a second feed or an identity-less mapping, and Plaid's documented id change would keep forcing the lists apart. Tables without a ladder were rejected because the constraints then refuse the duplicate feed but cannot say which row an account with a new id belongs to, so each path keeps its own matcher, which is how Link completion, reconnect, and account update came to disagree; a renamed id would land as a new provider account and the user would meet the duplicate again at setup. Matching on name alone was rejected because Sure had to fix a name-only relink that hijacked a live link. Keying import rows on a single provider transaction id was rejected because an import row's list of provider ids, with its history, is what lets the row survive a changed id.

## Consequences

Plaid Pattern and Sure, the maintained Maybe Finance fork, both model provider accounts as their own tables, and Sure still has the same duplicate-after-re-consent bug open; this is not a Caishen-only problem. The bank service splits along the seams it already has, connection lifecycle, identity and links, import application, and inbox projection, with public entry points keeping their names. The Banks panel shows each provider account's state so a stale balance has a visible reason. The administrative duplicate repair gains a same-connection mode for two provider accounts feeding two budget accounts where one is an unused duplicate, with the same preview, plan hash, and explicit apply as the existing repair. Once the tables are the source, a property test over random sequences of link, subset reconnect, account update, add accounts, disconnect, id change, and rename asserts that the budget account count never grows without an explicit new-account choice and that every live link has an identity.
